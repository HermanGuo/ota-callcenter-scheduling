# MVP 分阶段路线（OTA 呼叫中心一线）

总原则：**每一阶段结束都要有「能给真人演示」的东西。**

---

## 阶段 0 · 业务纸面（3 天内）

**交付：**
- 班次模板列表
- 技能列表
- 硬规则 / 软规则各若干条
- 一个真实小组的假数据（10～20 人）

**退出标准：** 你能向组长讲清楚「系统上线后他们怎么用」。

---

## 阶段 1 · MVP-0 手工排班（2～4 周）【从这里开始写代码】

**交付：**
- 员工 / 班次 / 周赋值
- 基础冲突检查
- 导出 Excel

**技术建议（小白）：**
- Python + Streamlit + CSV/SQLite
- 或：飞书多维表格先模拟流程，同时学 Python

**对照开源：** 只看 C 层 README（StaffScheduler / employee-shift-scheduler），不 fork。

**退出标准：** 组长愿意用你导出的表排下周班（哪怕还要手工改）。

---

## 阶段 2 · 需求人数（2～3 周）

**交付：**
- 输入：每 30 分钟预测话务 + AHT + SLA
- 输出：每时段「需要多少人在线」以及「考虑 shrinkage 后要排多少人」
- 班次覆盖：早班覆盖哪些时段（简单映射即可）

**对照开源：** mod_turbotab（精读）

**退出标准：** 排班时能看到「这个班缺口 3 人」而不是纯感觉。

---

## 阶段 3 · 自动初稿（3～6 周）

**交付：**
- 一键生成下周初稿
- 人可以在界面上改
- 标出违反硬约束的格子

**对照开源：**
- Python：roster-wizard / OR-Tools
- 或以后 Java：Timefold employee-scheduling

**退出标准：** 自动初稿能减少组长 50% 以上的填表时间。

---

## 阶段 4 · 能内部试用的系统（持续）

按优先级加：
1. 登录与角色（管理员 / 组长 / 坐席）
2. 换班申请与审批
3. 休假占坑
4. 发布与历史版本
5. 大促 / 航变的简易「加急班」标记
6. （更后）日内缺口看板

**对照开源：** aivot 的冲突解释、Shiftplan 的审计、reeforce 的日内思路。

---

## 建议的仓库结构（你自己的项目，以后再建）

```
ota-agent-roster/
  README.md
  docs/                 # 业务规则、名词表
  data/sample/          # 假数据
  app/                  # 你的小工具代码
  references/           # 可放本资料库的副本或链接
```

本资料仓库（`ota-callcenter-scheduling`）专门放「调研与学习」，和「你要上线的代码」分开，避免搅在一起。
